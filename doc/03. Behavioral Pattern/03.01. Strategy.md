# Strategy 패턴 정리

## 01. 개요

Strategy 패턴은 동일한 목적을 가진 여러 알고리즘을 각각 별도 클래스로 분리하고, 실행 시점에 원하는 알고리즘을 교체해서 사용할 수 있게 만드는 행동 패턴이다.

현재 프로젝트의 Strategy 예제는 버전이 올라갈수록 개선되는 흐름으로 구성되어 있다.

- `Strategy_CallCenterScheduler_Ver1`: 하드코딩 분기 방식
- `Strategy_CallCenterScheduler_Ver2`: 인터페이스 기반 Strategy 패턴 적용
- `Strategy_CallCenterScheduler_Ver3`: 전략 교체와 구조화된 결과를 지원하는 최종 개선형

---

## 02. 예제 도메인

예제는 콜센터 스케줄러를 기준으로 한다. 상담 전화를 어떤 기준으로 가져오고, 어떤 상담원에게 배분할지에 따라 전략이 달라진다.

현재 전략 구현 클래스는 다음과 같다.

- `Strategy_RoundRobin`
- `Strategy_LeastJob`
- `Strategy_PriorityAllocation`
- `Strategy_AgentGetCall`

각 전략은 아래 2가지 책임을 가진다.

- 다음 상담 전화를 어떤 기준으로 가져오는가
- 상담원을 어떤 기준으로 선택하는가

---

## 03. 구현별 분석

### 03.01. Ver1 - 하드코딩 분기

대상 파일:
- `src/03. Behavioral Pattern/Strategy/Strategy_CallCenterScheduler_Ver1.cs`

핵심 코드:

```csharp
switch (schedulerType)
{
    case "RoundRobin":
        ...
    case "LeastJob":
        ...
    case "PriorityAllocation":
        ...
}
```

설명:
- 스케줄러 클래스 안에서 문자열 분기로 모든 정책을 직접 처리한다.
- 가장 단순하지만 확장에 약한 구조다.

장점:
- 처음 이해하기 쉽다.
- 코드량이 적다.

단점:
- 새 전략이 추가될 때마다 기존 클래스를 수정해야 한다.
- 조건문이 계속 늘어난다.
- 테스트와 유지보수가 불편하다.

---

### 03.02. Ver2 - Strategy 패턴 기본형

대상 파일:
- `src/03. Behavioral Pattern/Strategy/Strategy_CallCenterScheduler_Ver2.cs`
- `src/03. Behavioral Pattern/Strategy/Strategy_Scheduler_Ver1.cs`

핵심 코드:

```csharp
public class Strategy_CallCenterScheduler_Ver2
{
    private readonly Strategy_Scheduler_Ver1 _scheduler;

    public Strategy_CallCenterScheduler_Ver2(Strategy_Scheduler_Ver1 scheduler)
    {
        _scheduler = scheduler;
    }
}
```

설명:
- 공통 동작 규약을 인터페이스로 분리한다.
- 실제 정책은 별도 전략 클래스로 위임한다.
- 컨텍스트는 구체 클래스가 아니라 인터페이스에만 의존한다.

장점:
- 새로운 전략을 추가해도 기존 컨텍스트 수정이 거의 없다.
- 테스트하기 쉬워진다.
- 객체지향적인 구조가 분명해진다.

단점:
- Ver1보다 클래스 수가 늘어난다.
- 패턴 개념을 모르면 처음에는 구조가 낯설 수 있다.

---

### 03.03. Ver3 - 최종 개선형

대상 파일:
- `src/03. Behavioral Pattern/Strategy/Strategy_CallCenterScheduler_Ver3.cs`
- `src/03. Behavioral Pattern/Strategy/Strategy_ScheduleResult_Ver3.cs`

핵심 코드:

```csharp
public void SetScheduler(Strategy_Scheduler_Ver1 scheduler)
{
    _scheduler = scheduler ?? throw new ArgumentNullException(nameof(scheduler));
}

public Strategy_ScheduleResult_Ver3 Run()
{
    return new Strategy_ScheduleResult_Ver3(
        _scheduler.Name,
        _scheduler.GetNextCall(),
        _scheduler.SendCallToAgent());
}
```

설명:
- 실행 중 전략 교체가 가능하다.
- 현재 어떤 전략이 사용 중인지 이름으로 확인할 수 있다.
- 실행 결과를 구조화된 객체로 반환해 테스트와 재사용성이 좋아진다.

장점:
- 런타임 전략 변경이 가능하다.
- 문자열이 아닌 결과 객체를 제공해 활용 범위가 넓다.
- 테스트 코드 작성이 쉬워진다.

단점:
- Ver1보다 구조가 복잡하다.
- 단순 예제에서는 다소 과하게 느껴질 수 있다.

---

## 04. 전략 구현 클래스

각 전략은 `Strategy_Scheduler_Ver1` 인터페이스를 구현한다.

### 04.01. Round Robin

- 전화를 순서대로 가져온다.
- 다음 순서 상담원에게 배분한다.

### 04.02. Least Job

- 대기열에서 상담 전화를 가져온다.
- 상담 대기가 가장 적은 상담원에게 배분한다.

### 04.03. Priority Allocation

- 우선순위가 높은 고객 전화를 먼저 가져온다.
- skill 값이 높은 상담원에게 우선 배분한다.

### 04.04. Agent Get Call

- 상담원이 직접 다음 전화를 가져간다.
- 상담원이 전화를 직접 가져가는 흐름을 표현한다.

## 05. 버전별 비교

| 구분 | Ver1 | Ver2 | Ver3 |
|---|---|---|---|
| 정책 선택 방식 | 문자열 분기 | 생성자 주입 | 생성자 주입 + 런타임 교체 |
| 확장성 | 낮음 | 좋음 | 가장 좋음 |
| 테스트 용이성 | 낮음 | 좋음 | 가장 좋음 |
| 반환 방식 | 문자열 | 문자열 | 결과 객체 |
| 학습 포인트 | 리팩터링 전 상태 | Strategy 패턴 기본형 | 실무형 개선 구조 |

---

## 06. Strategy 패턴의 장점

- 알고리즘을 독립 클래스로 분리할 수 있다.
- 조건문 중심 구조를 다형성 기반 구조로 바꿀 수 있다.
- 새 전략을 추가할 때 기존 코드 변경을 줄일 수 있다.
- 테스트가 쉬워진다.

---

## 07. Strategy 패턴 사용 시 주의점

### 07.01. 클래스 수 증가

전략마다 클래스가 하나씩 생기므로 구조가 커질 수 있다.

### 07.02. 너무 작은 차이에도 과도한 분리

전략 간 차이가 매우 작다면 오히려 구조만 복잡해질 수 있다.

### 07.03. 컨텍스트 책임 관리

컨텍스트가 전략 선택까지 과하게 담당하면 다시 조건문이 몰릴 수 있다. 전략 생성과 선택 책임도 적절히 분리하는 것이 좋다.

---

## 08. 현재 프로젝트 기준 해석

현재 프로젝트는 아래 흐름으로 읽으면 자연스럽다.

1. `Ver1`
하드코딩 분기 방식으로 시작

2. `Ver2`
인터페이스와 전략 클래스를 도입해 Strategy 패턴 적용

3. `Ver3`
전략 교체와 결과 객체까지 도입해 더 실용적인 구조로 개선

즉, 이 예제는 "조건문 기반 구현을 Strategy 패턴으로 리팩터링하고, 이후 테스트와 확장성을 고려해 더 개선하는 흐름"을 보여준다.
